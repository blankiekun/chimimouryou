# CLAUDE.md

chimimouryou: a fork of [ttu-ttu/ebook-reader](https://github.com/ttu-ttu/ebook-reader) (ッツ Ebook Reader), a browser-based EPUB/HTMLZ reader aimed at Japanese text, extended into a self-hosted reader for a Calibre library: accounts, sync, highlights, AI helpers, manga, difficulty estimates. It runs on any server with Docker (`docker-compose.yml`, guide in `docs/INSTALL.md`).

The details of a particular deployment (hosts, addresses, how it is deployed and rolled back) are in `CLAUDE.local.md` when present; it is not in git.

## Repository layout

- pnpm workspace: the only app is `apps/web`, a SvelteKit app built with `@sveltejs/adapter-static`.
  The output is purely static; there is no server-side code at runtime.
- `apps/desktop` (P5): an Electron shell serving the standalone build from `http://127.0.0.1:41917` with Yomitan loaded unmodified (`scripts/fetch-yomitan.sh`, pinned, not committed; `yomitan-shim.cjs` adds `chrome.permissions`); see its README. The Docker images never install it (`.dockerignore`, and web.Dockerfile copies only `apps/web/package.json` before `pnpm install`); Electron's binary is fetched by its `fetch` script, not on install.
- `apps/web/src/routes/`: pages. `b/` is the reader (`b/+page.svelte` is large), `m/` the manga reader, plus `manage/` (library), `settings/`, `statistics/` and `auth/`.
- `apps/web/src/lib/components/`: UI components. `book-reader/` is the reading view and `settings/` is the settings UI.
- `apps/web/src/lib/data/`: stores, settings enums and storage/database code. Books live in the browser (IndexedDB), synced with the server (Calibre source) or GDrive/OneDrive.
- `apps/web/src/lib/functions/`: parsing, file loaders and utilities.
- `scripts/calibre/`: the server side: nginx template, catalog builder and Python services (accounts, import, difficulty) with their tests.
- `docker/`, `docker-compose.yml`: the Docker install. `docker-compose.static.yml` is upstream's reader-only image.
- `scripts/deploy.sh`: deploys the working tree to a server (Proxmox container, SSH or local) and restarts the stack; reads the gitignored `local/` (`deploy.env`, `env`, optional override). `deploy/server/` holds the commands it installs (`ebook-compose`, `ebook-account`, `ebook-update`), `deploy/examples/` optional setups (`tailscale-https/`).
- Standalone edition (`VITE_EDITION=standalone`, `standalone` in `lib/data/env.ts`, D9): the same app without a server. Gate server features in `lib/` (data loaders return empty, `checkSession` null, `calibreSourceAvailable` false, the factory hands out the browser handler for Calibre) and hide their UI; it must send no request to `/calibre/` or `/account/` (`standalone.test.ts`). Published to GitHub Pages by `deploy/pages/pages.yml`. The service worker deletes only caches named `chimi:…` (`service-worker-caches.ts`).
  Analysis tools (Settings → Analysis tools, desktop only, `lib/data/analysis-tools.ts`): optional downloads built by `scripts/analysis-tools/build.sh` (sudachi.rs wasm with `sudachi-wasm.patch`, SudachiDict-core, Pyodide, yurigana, the difficulty service's Python, the chimi-difficulty models and onnxruntime-web's wasm; Pages builds it) into the `analysis-tools` cache, the dictionary and packs unpacked in OPFS (never precached). Two features, installed and removed apart (manifest `features` marks the files only one needs; shared files stay while either is installed): **difficulty estimates** (word list + estimate: reader-db `estimates`/`wordLists`, made on open, from the book page or in the background; Book words, coverage, the Difficulty box, library filters/sort and Read next) and **generated furigana** (readings file in reader-db `readings`, made only while the setting is on, which is the standalone default; turning it off in `/b` stops the reader's job). Each is its own pipeline (`browser.py` part `words` or `readings`) in two workers one after the other (`functions/analysis/`: Sudachi writes an OPFS token file, then Pyodide, rounds until no text is missing), plus `analysis-score.worker.ts` (onnxruntime-web) for the estimate; one job at a time, readings first, the reader's before the background's. Background analysis (`lib/data/background-analysis.ts`): a saved book (`BrowserStorageHandler.saveBook`) and, once per start from `/manage` when idle, every stored book without a current estimate/readings file are analysed one at a time (not manga/VNs; "Analysing N of M…" in the library); the first run offers the download (`analysisDownload$` keeps its progress for Settings) and the Generated furigana switch. `furiganaProgress$` shows furigana progress (and the server's queue) in the Aa sheet.
- Styling: Tailwind 3 + SCSS. Svelte 4 syntax in app code (not runes).

## Git workflow

- The fork's branch is `main` on GitHub; upstream is the `upstream` remote. Internal names (`ebook-reader` compose project, `/opt/ebook-reader`, `ttu-reader-data` sync root, `ttu_session` cookies) predate the name and stay: changing them would break existing installs.
- `main` only changes through pull requests with green CI (CONTRIBUTING.md → Pull requests): branch from `origin/main`, push, `gh pr create`, squash-merge. Never push to `main` directly.
- To pull upstream updates: a `sync/upstream` branch with `git merge upstream/main`, merged with a merge commit (`gh pr merge --merge`), never squashed.
- Commit with clear messages (`feat:`, `fix:`, `docs:` …) so changes are easy to rebase or merge against upstream.

## Server

- Docker stack (`docker-compose.yml`): `web` (nginx + the built app; `docker/40-ebook-reader.sh` creates `/data` for PUID/PGID, sets the nginx user and renders the nginx template), `account` and `catalog` (services image target `base`), and the optional profiles `import`, `difficulty` and `mokuro`. Paths come from the environment (`/library`, `/data/{sync,accounts,state}`); every setting is in `docs/CONFIGURATION.md`.
- nginx config: `scripts/calibre/nginx-ebook-reader.conf.template` (upstream's `default.conf` plus the Calibre and account locations), rendered by `render-nginx.sh` when the web container starts. Server-level extras (TLS, resolver, real IP) go in `/etc/nginx/ebook-reader.d/`.
- `DATA_PATH` holds everything the server stores: `sync/` (shared WebDAV folder, `/calibre/sync/`), `accounts/<account id>/` (per-account WebDAV, `/account/sync/`), `state/account/accounts.db`, `state/catalog/` (catalog, `no-cover.json`, `thumbs/`: card-sized covers, `/calibre/thumbs/`), `state/import/` (queue, `jobs.json`, `calibre-write.lock`), `state/difficulty/` (results, `frequency-dictionary.zip`, optional `term-dictionaries/`). Account data includes synced AI keys: never put `DATA_PATH` on storage other machines can read.
- Browser storage (settings, cached books, highlights) is per origin, so an HTTP and an HTTPS address of the same server don't share it. Calibre books and their progress, statistics and highlights come back from the server. Over plain HTTP the service worker/offline mode and some File System Access features don't work.

## Features (not upstream)

- Calibre library (`/calibre/catalog.json`, files at `/calibre/library/`, read-only; only book files and covers are served).
  The catalog is built from a copy of `metadata.db` by `build-catalog.py` (the `catalog` service, every `CATALOG_INTERVAL` seconds, only when the DB changed).
- Calibre is the default storage source (`StorageKey.CALIBRE`, `lib/data/storage/handler/calibre-handler.ts`). The Browser source is only offered in builds that default to it (`browserSourceAvailable`, `fallbackStorageSource` in `storage-view.ts`: the reader-only static build); the browser handler stays as every source's IndexedDB cache. Signed out where reads need an account, the catalog's 401 lists an empty library that asks to sign in.
  The library lists the whole catalog. Opening a book for the first time downloads it from Calibre, processes it, and uploads the processed data to the server (not for manga: every device loads the CBZ itself).
  Reader data (book data, progress, statistics) syncs through nginx WebDAV at `/calibre/sync/`, with the same folder-per-title layout as GDrive. Sync for Calibre books is always on, regardless of the auto-replication setting.
  Books are identified by title, so the catalog makes duplicate Calibre titles unique by appending ` (author)` or ` [id]`.
  Importing a file into the Calibre source adds it to the Calibre library (accounts with the `import` permission): `lib/data/calibre-import.ts` uploads to `/calibre/import/api/` (`scripts/calibre/import/service.py`), a queue that runs `calibredb add` one book at a time and then rebuilds the catalog. It is the only writer of `metadata.db`; Calibre's own title+author check refuses duplicates. Afterwards the library is refreshed and books whose title names an existing series are offered for it. Admins deleting Calibre books in the library also remove them from it (`removeFromCalibre` → `POST remove`: `calibredb remove`, i.e. Calibre's recycle bin; game folders are deleted). `build-catalog.py` takes a lock (`catalog.json.lock`) and gives `catalog.json` its inputs' mtime, so builds from the timer and the queue don't race.
  Series made by readers (library select mode → "Make series", `book-card/series-dialog.svelte`, `lib/data/series-overrides.ts`, `series` permission) are shared by everyone in `/calibre/sync/series.json`, keyed by title; they override the catalog's series (an empty series removes a book from one) and are applied in `CalibreStorageHandler.getBookList`.
  Calibre books are cached in the browser (IndexedDB) and only re-downloaded when the server copy is newer. The "External Read" hint is skipped for them.
  When the server can't be reached (fetch `TypeError`), `getBookList` lists the cached books instead (`cachedBookList`, `libraryOffline$` → banner with retry in `/manage`, retried on `online`), and `/b` opens a cached book when sync fails (like `/m` and `/v`); failed uploads stay queued and retry on the next save or `online`. Home books (My books + Continue reading, not VNs) are downloaded in the background from `/manage` (`lib/data/offline-books.ts`, own handler instances, one at a time; `saveLocally` uses its own browser handler for the same reason).
  Books without a Calibre cover get one: the catalog builder extracts it from the EPUB into the book's folder as `cover.jpg` (JPEG unchanged, other formats converted at full size; never overwrites; `metadata.db` is not modified, so Calibre's `has_cover` stays unset). Cover detection: OPF cover-image / `meta name=cover` / guide cover page / item named "cover" / first image on the first pages / first manifest image; SVG/XHTML cover pages are followed to their image. EPUBs without a usable one are remembered in `state/catalog/no-cover.json` (raise `COVER_EXTRACTOR_VERSION` to retry them). The builder must run as the library owner (`PUID`).
  The catalog skips non-zip EPUBs, such as macOS `._` resource forks that were imported into Calibre.
  It also carries tags, rating and publisher, and a series for every book: Calibre's own series, or one inferred from volume numbers in titles (`split_volume` in `build-catalog.py`, `seriesInferred: true`).
  `scripts/calibre/assign-series.py` writes such series into Calibre itself (in the `import` container: `docker compose exec import calibre-debug -e /app/assign-series.py -- [--apply]`), using the same title parsing: books without a series join a matching Calibre series (width/case ignored) or, two or more distinct volumes with a common author, form a new one; books by another author (e.g. manga adaptations) are left out. It also merges series that are one work (`merge_plan`, sharing an author): names that differ only in width, case, spaces, punctuation or store tags like 【電子版限定特典付き】 (`merge_key`, letters and digits only; the spelling found in most book titles wins), and series named after one volume (`volume_series`: digits only, not 上/中/下; a misnamed main series keeps its indexes, per-volume part series get N.part, sequels like はやて×ブレード2 stay apart). Store tags are also left out of new series names. Dry run by default; `--apply` copies `metadata.db` to `state/import/backups/` (last 5) and writes through Calibre's API under the import queue's lock; `--json` for machines. Admin panel → Tools → Series runs it through the import service (`POST /calibre/import/api/series`, admins only via nginx `/_account_admin`, `components/admin/series-tool.svelte`).
- Reader extras:
  - "Listen" (the reader panel's Listen tab, `book-reader/listen-panel.svelte`; stays mounted when the panel closes, so playback goes on) has two modes. **Audiobook** (`audiobook-player.svelte`, `data/audiobook.ts`): an audio file plus SRT/VTT subtitles, matched to the book by `matchCues` (`functions/audiobook/subtitles.ts`, exact match, then trigram voting), stored in IndexedDB (`audiobooks`; the playback position is in localStorage so the blob is never rewritten). **AI voice** (`tts-player.svelte`, `lib/data/tts.ts`) reads from the current position without furigana.
    Both send the line being read as character counts; `showReading` in `b/+page.svelte` draws it as the `ttu-reading` CSS highlight and scrolls/turns the page when it isn't visible.
    Without an ElevenLabs voice connection with a key on this device (or with the voice feature set to `deviceVoice`, `'device'`) the AI voice reads with the device's Web Speech voices (`speechSynthesis`, `deviceVoiceName$` per browser, Japanese first, Settings → AI → Voice, `settings-ai-voice.svelte`); `boundary` events give the phrase highlight (`spokenPhrases` + `timelineEntryAt`), and the whole chunk stays lit when a voice sends none. Anki's AI sentence-audio fallback still needs ElevenLabs.
    With one, the AI voice calls ElevenLabs directly from the browser (`elevenLabsVoice()` in `tts.ts`: the key from `aiConnectionKeys$`, never the mirrored `elevenLabsApiKey$`; `POST <endpoint>/text-to-speech/<voice>/with-timestamps`, `xi-api-key`, the voice feature's model, default `eleven_v4`; voices listed from `/v1/voices` into the connection cache's `voiceList`) in chunks of 200-800 characters with `previous_text`/`next_text`. The character timestamps become a phrase timeline (`readingTimeline` in `data/tts.ts`) that drives the highlight. Audio is cached around the current chunk only (`data/tts-audio-cache.ts`).
  - Selecting text shows a toolbar (`book-reader/selection-toolbar.svelte`): four highlight colours, "Note", and "Ask AI" (`book-reader/ask-ai-panel.svelte`, `lib/data/ask-ai.ts`), which streams from OpenRouter chat completions and has preset buttons (Settings → AI).
  - Furigana style "Known" (`FuriganaStyle.Known`, `lib/data/known-furigana.ts`): `reactiveElements` marks each rendered section's `<ruby>` as `ttu-known-ruby` (hidden, click toggles) when every kanji was met `knownKanjiMinCount` (10) times in `kanji-seen` (all books, read once per opened book) and the ruby is hiragana spelled by the kanji's readings (`isPlainReading`/`hideKnownRuby` and `yurigana/kanji-readings.json` from the yurigana package, KANJIDIC2, rendaku/っ allowed); anything else (katakana, kanji, gikun, jukujikun) stays shown.
  - Generated furigana (`generatedFurigana$`, Settings → Reader next to Hide furigana, with the first-open wait in its description, `lib/data/generated-furigana.ts`): for Calibre books `/b` requests the difficulty service's readings file (POST, polls while queued: 3, 5, 10 s, then every 15 s); the last one is kept in reader-db `readings` (deleted with the book or on "Remove from Home", `deleteCachedReadings`, like `deleteVnCache`) and rendered at once, the server is asked again in the background (`If-None-Match` its ETag, 304 when unchanged) and a different file re-renders; Home's books are fetched ahead from `/manage` after `keepBooksOffline` (`prefetchReadings`, one every 30 s for the nginx rate limit, kept ones skipped) and a book's page asks for its file on open, and `addGeneratedRuby` wraps its glosses in `<ruby class="ttu-gen-ruby">` in `elementHtml` before rendering (skipped when its `characters` differ from the book's count; `rt` isn't counted). A file that gets ready, or the setting, re-renders the book at the current position. Coloured towards `--accent-color` in `book-reader/styles.scss`.
  - Search (magnifying glass or Ctrl+F, `book-reader/book-search-panel.svelte`, `lib/functions/book-text/book-search.ts`) searches the rendered text, furigana excluded, and jumps by character count like a bookmark.
  - Highlights and notes (`lib/data/annotations.ts`, reader panel → Highlights) are anchored by character counts (`lib/functions/book-text/text-positions.ts`) and drawn with the CSS Custom Highlight API, so the book DOM is never modified.
    They are stored in IndexedDB (`ttu-annotations`, opened by `data/reader-db.ts`, which also holds recaps, lorebooks, audiobooks and kanji seen); the cache of a synced book records its owning account and is ignored under another sign-in state. Calibre books also sync them as `annotations.json` in the book's WebDAV folder (merged per highlight, newest edit wins, deletions kept as tombstones).
  - Extra sync files (`lib/data/sync-files.ts`): highlights, recaps, lorebook and VN saves sync in the book's folder on its own source (`bookSyncSource`: the book's `storageSource`, else the auto-replication target), kanji, word marks and settings at the root: the account's `/account/sync/` while signed in, else the library's Drive/OneDrive/folder (`readerSyncSource`; settings then without API keys). Handlers implement `readSyncFile`/`writeSyncFile` (Calibre statically, same URLs as before; Drive, OneDrive and folders on own instances that never prompt, writing only into book folders that exist); `syncJsonFile` reads, merges and writes, retrying once on `SyncConflictError` (Drive `version`, OneDrive eTag/If-Match, folder modified time; nginx WebDAV can't check).
    `BookmarkManager.getRenderedStartCount()` gives the character count where the rendered DOM starts (the current section in paginated mode).
  - Manga (`lib/data/manga.ts`, reader `routes/m/+page.svelte`): CBZ/ZIP files load with `functions/file-loaders/cbz/load-cbz.ts` into an ordinary book record, so library, IndexedDB and sync are unchanged. The pages are the blobs; `elementHtml` is `<!--ttu-manga-->` plus the page names as JSON (`isManga`, `mangaPages`), `characters` is the page count, and the bookmark stores the page index as `exploredCharCount`. `/b` redirects manga to `/m`, which has none of the book extras. Reading mode (rtl/ltr/vertical) is kept per series (`seriesReadingMode`: `mangaSeriesModes$`, synced in `sharedSettings`; the series comes with `adjacentVolumes`, so offline or outside a series it is the last mode chosen, `mangaReadingMode$`); the reader settings (`mangaScale$`, `mangaDualPage$`, background, double tap, tap zones `mangaTapLayout$`/`mangaTapInvert$` with Mihon's layouts in `tapDirection`, wake lock, page number) are per browser. Paged modes handle their own gestures (`touch-action: none`): pan/pinch/double tap/Ctrl+wheel zoom, swipes drag a track of the previous, current and next spread (`pageSpreads`: cover, wide pages and the last page alone; `fitSize`, `clampPan` in `manga.ts`); the bookmark keeps the first page of the spread shown (the last page on the last spread), and a resize keeps the zoom. Calibre manga link to the volumes before and after (`adjacentVolumes`: catalog plus series overrides, CBZ/ZIP only, Store order): turning past either end shows `manga/volume-transition.svelte`, turning on opens the volume (`openVolume`: Calibre handler's `prepareBookForReading`, then `/b`).
    Text (mokuro, `lib/data/mokuro.ts`, `mokuro` profile, `scripts/calibre/mokuro/service.py`): per catalog id in `state/mokuro/<id>.json` (nginx `/calibre/mokuro/<id>.json`; pages by CBZ path, else file name, else order: `pagesText`), made by the service running the `mokuro` CLI on the CBZ (one volume at a time, queue, progress from mokuro's `_ocr` cache) or uploaded as a `.mokuro` (`convert` validates it); API `/calibre/mokuro/api/` needs `import`. `/m` lays it over each page (`manga/mokuro-overlay.svelte`, percent boxes, font from the rendered height; `mangaText$` hover/always/off); the book page's Text row is `book-card/mokuro-text.svelte`. Not cached for offline reading.
    The catalog lists CBZ and ZIP files that are mostly images (`manga_pages`/`is_valid_book` in `build-catalog.py`; ZIPs that wrap EPUBs are skipped), with the first page as `cover.jpg`. The import service queues `.zip` as `.cbz` (Calibre would unpack a `.zip`) and passes the file name as `--title`. The difficulty service ignores manga but scores visual novels from their scripts (`vn_text` in `jiten/features.py`; game folders are mounted at `/vn` there too).
  - Visual novels (`lib/data/vn.ts`, player `routes/v/+page.svelte`): a ZIP holding an ONScripter script (`findVnRoot`: `0.txt`, `00.txt`, `nscript.dat`…) is loaded by `loadCbz` → `file-loaders/vn/load-vn.ts` into a book record like manga: the game files are the blobs (paths relative to the game folder), `elementHtml` is `<!--ttu-vn-->` plus `{encoding, files}` (`isVn`, `vnInfo`), `characters` the script's text (`scriptCharacters`). `/b` redirects them to `/v`.
    The engine is CONscripter (https://github.com/blankiekun/CONscripter, the owner's fork of ONScripter-yuri, GPL-2.0) fetched by `scripts/conscripter/build.sh` from the web build (`conscripter_<tag>_web.7z`) of its latest GitHub release, or `CONSCRIPTER_TAG`, checked against `scripts/conscripter/sha256sums` (`CONSCRIPTER_RECORD=1` adds a new release's; ebook-update reads main's copy), into `static/vn/conscripter.{js,wasm}` and `conscripter-version.txt` (committed; rerun after a CONscripter release, nothing updates automatically; admin panel → Tools → Visual novel engine, `engine-tool.svelte`, `checkEngineRelease`, shows whether one is out and installs it through `ebook-update`: an `{"engine": tag}` request runs `build.sh` with `CONSCRIPTER_OUT` into `DATA_PATH/state/engine`, which nginx serves ahead of the built-in files (`ENGINE_DIR`, no build or restart); the web container's start removes it once the built-in engine is the same or newer; the service worker fetches the engine network-first into its own `vn-engine` cache rather than precaching it). `static/vn/player.html`/`player.js` run it in a same-origin iframe outside SvelteKit's CSP; `startGame()` lazy-loads game files from blob URLs, mounts saves on IDBFS (`/save/<hash of title>`) and falls back to `static/vn/default.ttf` (Noto Sans JP).
    CONscripter (v0.9.0+, formerly our `text-hook.patch`) calls `self.consText(bytes, skipped, boxes)` (the hooks, `g_cons_*` globals and `cons()` loader are the engine's API; v0.23.0 renamed them from ONScripter-yuri's `onsyuri*`, and `build.sh` refuses older releases) at every click wait with the current page's raw text (ruby as `(base/reading)`) and where `drawChar` drew each of its characters (byte offset, x, y, font size; ruby readings excluded). The page turns the boxes into screen lines (`overlayLines`) for `player.js`'s `showText`, which lays them as transparent text over the canvas for Yomitan (`#page-text`, one absolutely positioned div per line; clicks on the text are re-dispatched to the canvas). Choices and system menu items come from `getSelectableSentence` as `self.consChoice(bytes, x, y, size, pitch)` (`#choices`). The engine drives clearing through `self.consOverlay(event)`: `page` (newPage), `hide`/`show` (text window hidden and back, page kept), `choices` (deleteButtonLink), `enter`/`leave` (system menu or backlog; page and choices stashed and restored), `reset` (left it elsewhere); input never clears it. Backlogs (v0.12.0+): the built-in lookback sends each page as `self.consBacklog(bytes, boxes)`, and at every wait for input `self.consSprites(bytes, boxes)` sends the visible `strsp` sprites (script-drawn backlogs and menus, `#sprite-text`); `player.js` lays both out with the page's `textLines` option (`overlayLines`). It also decodes the text (`decodeText`) for the optional panel below the game (`parseVnPage`, `vnTextPanel`) and counts what was added (`newText`, page hashes in reader-db `vnRead` so rereads count nothing; nor does text the engine reports as read before through `self.consPosition`'s `read`, its kidoku data) for progress (`exploredCharCount`), statistics (`updateStatistic` from the tracker module) and kanji (`recordKanjiText`).
    v0.19.0+ hooks: `self.consVoice(channel, file)` (channel 0 kept as the line's voice, backlog pages bring theirs), `self.consMode(auto, skip)`; the page calls the module's `_consSet{Auto,Skip,Ruby,TextSpeed}` through `player.js`'s `engineSet` (guarded, so older engines still run): the header's furigana and instant-text toggles (`vnFurigana`, `vnInstantText` in localStorage), and Yomitan's scan keys (modifiers) stop auto mode. Movies (`playVideo`, `playVideoHold` for `mpeghold`, `consMovie*` for movies drawn as pictures) are ported from CONscripter's `src/cons_web/conscripter.html`; the engine calls them unguarded, so a new engine's shell functions must exist in `player.js`. `consWindow`, `consTrace` and `consPreload` are unused.
    Games can also be unpacked folders in `VN_PATH` (mounted at `/vn` in web, catalog, import and difficulty; nginx `/calibre/vn/` with JSON listings, `VN_DIR` in `render-nginx.sh`): `vn_games` in `build-catalog.py` lists each folder (format `VN`, negative id from the name, `file` = the script's folder, cover relative to `VN_PATH`), the handler's `processCalibreBook` stores only `loadVnFolder`'s file list and script analysis (`VnInfo.base`, no blobs), and the player fetches files by URL (games over 10 MB offer to keep them in the Cache API, `vnCacheName`, `gameCache` in `routes/v/+page.svelte`, deleted with the book or on "Remove from Home" by `deleteVnCache`; files over 1 MB show a progress bar).
    Imported ZIPs that hold a game go through the import service like books, but its worker unpacks them into `VN_DIR/<file name>` (`add_vn`: only the script's folder, no `..`, free-space check, Shift JIS names via `zip_name`; up to `MAX_VN_BYTES`, nginx streams uploads) instead of `calibredb add`; the import container mounts `/vn` read-write. Admin panel → Tools → Catalog (`catalog-tool.svelte`) posts `/calibre/import/api/catalog` (admins only), which runs `build-calibre-catalog … --force`.
    Calibre games' saves sync as `vnsaves.json` (personal, base64 per save file, newest wins, `mergeVnSaves`; each file carries the `engine` version that wrote it, and `/v` shows a dismissable notice when `newerSaveEngine` finds one newer than `conscripter-version.txt`). The catalog lists CBZ/ZIPs with a script and marks them `vn` (not manga).

  Word frequencies come from Jiten's Yomitan frequency list (`state/difficulty/frequency-dictionary.zip`; `jiten_freq_global.zip` from jiten.moe/frequency-dictionaries is bundled in `jiten/data/` (CC BY-SA 4.0, README there) and copied there on start when missing by `install_bundled_dictionary` (`copy2`, so the pack `.key` is the same for one file); replaceable by admins from the panel ("Replace frequency list"), `POST dictionary`: nginx `_account_admin`, and the service checks `X-Account-Admin` too; checked by `install_dictionary`: at least `MIN_DICTIONARY_TERMS` (50,000) terms, and replacing an installed list needs `?force=1` when the readings of its 5,000 most frequent forms agree on under 95%, `reading_agreement` in `frequency.py`, which the panel confirms with the share); there is no frequency table built from the library any more.
  The model, chimi-difficulty (`jiten/chimi-difficulty.onnx`, built by `jiten/distil/`, README there), is Jiten's 55 features plus `EXTRA_FEATURES` (`features.py`: log characters and unique kanji, coverage ranks, MATTR, 連体形+noun relative clauses and predicates per sentence, hiragana share, non-常用 kanji, ruby), trained on jiten.moe's algorithmic scores; `-low`/`-high` models give the 10-90% range (widened by `chimi-difficulty-range.json`) (`low`/`high` in the results), `words95` the common words for 95% coverage. Word origins come from `goshu.json.gz` (UniDic), kanji grades from `kanji-grades.json` (KANJIDIC2), both built by `distil/make_tables.py`. Estimates carry `model` (`MODEL_VERSION`); "Books without an estimate" redoes those made by another model.
  Each estimate also stores `uniqueWords` and `tokens` (the word list's rows and occurrences before the cap, without noise) and writes the book's kanji counts (`state/difficulty/kanji/<id>.json.gz`, `GET /calibre/difficulty/api/kanji/<id>`) and its 2,000 most frequent words with their frequency rank (`save_words`, `state/difficulty/words/<id>.json.gz`, `GET …/words/<id>`, `[form, reading, count, rank, lemma]` (lemma: Sudachi's normalized form, so 分かる/わかる/判る share one; Anki words and marks match on form or lemma), one row per reading met (per occurrence from yurigana's `Reader`, as readings files read it, without name-ruby carry; one per worker, tokenizing through the Analyzer (`Analyzer.tokens`); a row takes the reading of a Reader word over exactly its head token, so counter spans (三本) aren't rows and tokens in Reader compounds keep Sudachi's: the readings in context are the yurigana package (https://github.com/blankiekun/yurigana, pinned by tag in `jiten/requirements.txt` and `apps/web/package.json`; `book_text`/`aozora_text` with ruby hints, Sudachi tokens), checked against Jiten's reading list; the server's own `state/difficulty/reading-model.json.gz`, when built (optional, none by default: `python -m yurigana.reading_context build` in the difficulty container), wins over yurigana's public table; described in docs/READINGS.md and yurigana's README; never commit a table or rows built from copyrighted books); counted in `Analysis.readings`; conjugated occurrences go to the most common one, words met only conjugated to the form's most common reading in the book, else Sudachi's reading of the form (`Analysis.form_readings`); rows of one form and reading from different Sudachi words are merged; the features keep the first occurrence's), names, affixes, particles and auxiliaries (by part of speech) left out; "Books without an estimate" also redoes estimates without one or with an older `WORDS_VERSION`, stored as `words` in the estimate). `python -m yurigana.evaluate` and `yurigana.reading_context` (`mine`, `report`) measure readings in context (the rows are book text: scratch, never git); a yurigana bump that changes readings needs a `WORDS_VERSION` bump. `distil/validate_speed.py` checks estimates against readers' reading speed once there are enough statistics.
  Readings files (#17, `jiten/readings_file.py`, `ReadingsQueue` in `service.py`, docs/READINGS.md → Readings files): `POST /calibre/difficulty/api/readings/<id>` (nginx `_account_shared`, `limit_req` zone `readings`) queues one from the reader's own processed book (`staticdata.json` of the newest `bookdata_*.zip` in the title's `/data/sync` folder, mounted read-only; `sanitize_for_filename` ports `sanitizeForFilename`), counted like the reader (`fixtures/character-count.json`, checked by Python and Vitest); one worker process with a yurigana `Reader`, outside the estimate jobs; `state/difficulty/readings/<id>.json.gz`, stale when `READINGS_VERSION`, yurigana's version or the bookdata name differ (a newer bookdata with the same `elementHtml`, by the file's sha256 `html`, keeps it: `retarget`); a file takes ~3 s and the worker stays `READINGS_KEEP_ALIVE` (2 min) after its last file. Every worker (estimates too) loads its Reader from `state/difficulty/reader.ygp` (`READER_PACK`, yurigana's `Reader.save`/`Reader.load`, mmap: ~0 s and ~100 MB instead of ~20 s and ~620 MB, pages shared), and its `FrequencyTable` from `frequency.ygp` (`FREQUENCY_PACK`, `save`/`load_packed`, ~450 MB as dicts), both built in a child process by `ensure_reader_pack` before a pool starts when its `.key` (`reader_pack_key`: yurigana version, frequency list, term dictionaries) differs; without it a worker builds its own. The reader uses them for generated furigana.
  jiten.moe itself scores with a private sentence-level model on RunPod (`DifficultyComputationJob` in Jiten's repo); the public `.onnx` is unused there.
  Jiten's API is for personal projects and small-scale research only (jiten.moe/guides/api-and-scraping): the training data was one list request plus one request per matched series, at most 75 a minute. The service doesn't call it; the app only searches it on request from a book's page (Find details).

## Commands and tests

- Front end (Node 24, pnpm 10 from `packageManager`): `pnpm test` (Vitest + jsdom, `src/**/*.test.ts`) and `pnpm check` (svelte-check) in `apps/web`, `npx eslint .` from the repo root. Without Node installed, run them in a `node:24-slim` container (CONTRIBUTING.md).
- Python tests: `python3 -m unittest discover -s scripts/calibre/tests` (standard library plus yurigana: `pip install --no-deps` its line of `jiten/requirements.txt`, or put its source on `PYTHONPATH`).
- Baseline: tests all pass, ESLint is clean, `pnpm check` has 13 pre-existing errors (`skipLibCheck` hides the libraries' own). Keep it that way.
- When dependencies change, regenerate `pnpm-lock.yaml` with pnpm 10 (`pnpm install --no-frozen-lockfile`; `CI=true` forces frozen mode); image builds use `--frozen-lockfile`.
- Svelte compiles with `immutable: true` (upstream `svelte.config.js`): assign new objects/arrays/Sets, never mutate and reassign the same one, or nothing re-renders.

## Fragile areas

- `routes/b/+page.svelte`: huge; the reader extras' glue lives inline. Keep new logic in `lib/` modules with tests and verify with a real book in both view modes.
- Sync file names carry metadata (`bookdata_*`, `progress_*`, upstream's `BaseStorageHandler`); renaming or adding prefixes affects every device.
- Book titles are identities (folder names). Changing how `build-catalog.py` makes titles unique orphans synced data.
- `scripts/deploy.sh`: the server-side steps are single-quoted `bash -c '…'` strings run through `run`; a single quote inside one ends it early. Over SSH they are re-quoted with `printf %q`, so keep them plain bash.
- `local/` and `CLAUDE.local.md` are gitignored and hold one deployment's settings; never commit them.
- The nginx template is rendered with `envsubst` limited to its own `${…}` names (`render-nginx.sh`); new placeholders must be added to that list, and nginx's own `$variables` must stay unbraced or unlisted.

## Verifying changes

After deploying, check that the pages load (`/`, `/manage`, `/settings`, `/version.txt`) over HTTP and HTTPS, and that `/version.txt` shows the commit.
`pnpm check` has pre-existing errors (e.g. `PasswordCredential`, `on:swipe`); only new ones matter.
For UI changes, verify the relevant route in a browser if possible. Reader changes need an actual book loaded, which is stored per browser.
